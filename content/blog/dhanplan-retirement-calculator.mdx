<AnswerBox>
Most retirement calculators are US-bound templates with a rupee symbol. DhanPlan treats Indian instruments — SIP, EPF, PPF, NPS, FIRE — as first-class columns, each with institutional-grade assumptions. It taught me that scope discipline and honest model math beat feature ceilings.
</AnswerBox>

Every retirement calculator I tried asked me about my 401k. I don't have a 401k. Nobody in India has a 401k. What we have is EPF with a ₹2.5L interest-tax threshold, PPF with a 15-year lock-in, NPS with a 60/40 lumpsum-annuity split, and SIPs with step-ups — and not one mainstream calculator models any of it honestly. DhanPlan started as that irritation, and it became the clearest product lesson I've shipped: **in a financial product, the model *is* the product.**

## The scope decision

We shipped four modules before adding anything else:

<Figure src="/blog-assets/dhanplan/modules.svg" alt="DhanPlan modules: SIP, EPF/PPF, NPS, FIRE — each with its own projection logic" caption="Four modules, each with institutional-grade assumptions. Scope discipline killed feature-creep in week one." />

- **SIP** — equity growth with inflation-adjusted terms, step-up SIP support, XIRR output.
- **EPF & PPF** — the two most Indian fixed instruments, with their year caps, interest-rate history, and tax treatment baked in.
- **NPS** — the worker's savings-with-tax angle: Tier I/II, asset allocation, partial withdrawal rules.
- **FIRE** — the retirement milestone everyone in 2026 asks for: coast FIRE, lean FIRE, fat FIRE, with real-growth math.

Each module gets its own projection logic; the UI is honest that no model predicts a market.

## The instrument specs (what we actually modeled)

### SIP — Systematic Investment Plan
- **Growth engine**: equity CAGR (user input, default 12%) with inflation adjustment (default 6%)
- **Step-up SIP**: annual increase % (default 10%), compounding on increased amount
- **XIRR output**: calculates actual return on irregular cash flows
- **Tax**: LTCG 10% >₹1L, STCG 15%, grandfathering (Jan 31 2018)
- **Sources**: SEBI mutual fund regulations, AMFI historical NAVs, CBDT notifications

### EPF & PPF — The Fixed-Income Duo

| Parameter | EPF | PPF |
|-----------|-----|-----|
| Contribution | 12% basic + DA (employer + employee) | ₹500–1.5L/year voluntary |
| Interest rate | EPFO declared (8.25% FY24) | Govt quarterly (7.1% Q1 FY25) |
| Tax regime (old) | EEE | EEE |
| Tax regime (new) | EET (interest >₹2.5L taxable) | EEE |
| Lock-in | Retirement / 2 months unemployment | 15 years (extendable 5-yr blocks) |
| Withdrawal | Partial: marriage, education, medical | Partial: year 7 onward (50% of balance 4 yrs prior) |

Sources: [EPFO notifications](https://www.epfindia.gov.in/), PPF Scheme 1968 (amended), Finance Acts 2020/2023.

### NPS — National Pension System
- **Tier I** (mandatory, tax-advantaged): 60% lumpsum (tax-free), 40% annuity (taxable)
- **Tier II** (voluntary, no tax benefit): liquid, no lock-in
- **Asset allocation**: Auto choice (age-based E/C/G) or Active choice (max 75% E)
- **Partial withdrawal**: 25% of contributions after 3 years (specific purposes only)
- **Annuity providers**: LIC, HDFC, ICICI, SBI, etc. — rates vary 5–7%
- Source: [PFRDA regulations](https://www.pfrda.org.in/), NPS Trust circulars

### FIRE — Financial Independence, Retire Early
Four variants, each with distinct math:
- **Coast FIRE**: invest early, stop contributing, let compounding hit target
- **Lean FIRE**: minimal expenses (₹3–5L/yr), high savings rate (>70%)
- **Fat FIRE**: comfortable expenses (₹15–30L/yr), lower savings rate
- **Barista FIRE**: part-time work covers expenses, portfolio covers rest

Each uses: `target = annual_expenses × 25` (4% SWR) adjusted for Indian inflation (6–7% long-term).

## What made it ship

The scoping rule was: **a feature must be defensible by two public data points.** If we couldn't cite the instrument's mechanics from an official source, it didn't ship. This killed feature-creep in week one.

Tests are part of the product. Breakage here loses trust along with money — we wrote **28 reconciliation tests** covering:

| Test category | Count | Examples |
|---------------|-------|----------|
| Year-cap boundaries | 6 | EPF ₹2.5L interest threshold, PPF ₹1.5L contribution cap |
| Tax regimes | 8 | Old vs new regime for each instrument, LTCG grandfathering |
| Inflation scenarios | 5 | 4%, 6%, 7%, 8%, variable year-by-year |
| Year-cap transitions | 4 | EPF interest taxability at ₹2.5L, NPS Tier I lumpsum tax |
| FIRE variants | 5 | Coast/Lean/Fat/Barista convergence tests |

Each test is a known-input → expected-output assertion against the projection engine. CI runs them on every push.

## What the product taught me

- **Model quality over field count.** Four truthful modules out-rank twenty wish-list fields.
- **Tests are part of the product.** A user who can't reconcile a number won't come back.
- **The boring math is the feature.** Inflation surfacing per row is the retention wedge.

### The inflation wedge (the feature that retained users)

We added a "real growth" column to every projection row: `nominal_return - inflation`. Users who saw their ₹1Cr corpus becoming ₹40L in today's money at 6% inflation over 20 years — that column drove 3× more return visits than the nominal projection alone. Mental accounting hates hidden inflation; surfacing it builds trust.

## The projection engine (how the math actually runs)

The engine is a pure TypeScript library — no framework dependencies, runs in browser or Node. Core abstraction:

```typescript
// projection-engine.ts
interface Instrument {
  project(inputs: Inputs, years: number): ProjectionRow[];
}

interface ProjectionRow {
  year: number;
  nominalValue: number;
  realValue: number;        // inflation-adjusted
  contributed: number;
  inflationRate: number;
  realGrowth: number;       // the retention wedge
}

class SIPEngine implements Instrument {
  project(inputs: SIPInputs, years: number): ProjectionRow[] {
    const rows: ProjectionRow[] = [];
    let corpus = 0;
    let contributed = 0;
    
    for (let y = 1; y <= years; y++) {
      const monthlySIP = inputs.monthlyAmount * Math.pow(1 + inputs.stepUpRate, y - 1);
      const annualContribution = monthlySIP * 12;
      contributed += annualContribution;
      
      // Compound with inflation-adjusted return
      const realRate = (1 + inputs.equityCAGR) / (1 + inputs.inflation) - 1;
      corpus = corpus * (1 + inputs.equityCAGR) + annualContribution;
      
      const realValue = corpus / Math.pow(1 + inputs.inflation, y);
      
      rows.push({
        year: y,
        nominalValue: corpus,
        realValue,
        contributed,
        inflationRate: inputs.inflation,
        realGrowth: realValue - contributed
      });
    }
    return rows;
  }
}
```

Each module (SIP, EPF, PPF, NPS, FIRE) implements `Instrument` with its own rules — caps, tax regimes, withdrawal rules. The orchestrator just calls `project()` on each and merges by year.

            const out = new EPFEngine().project({basic: 15000, da: 5000}, 30);

Coverage threshold: 90% on projection logic, 100% on tax math.

## What I'd do differently

- **Let the modules export a plan** (CSV/JSON) before inviting login walls — export early, gate later.
- **Carve the inflation story harder.** Users mentally undercount inflation; surfacing each row's real-growth number is the retention wedge.
- **Build the tax comparator earlier.** Old vs new regime comparison per instrument was the #1 support query; should've been a first-class view.

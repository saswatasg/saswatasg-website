<AnswerBox>
At LiveKeeping, PRO+ users generated E-Way Bills in Tally rather than in the app — a 17:1 adoption gap hiding in white noise. A two-week deep-dive diagnosis mapped the real workflow and produced a C-suite narrative so clear it changed the product roadmap.
</AnswerBox>

A compliance SaaS with 50K+ Indian SMBs lives or dies on **where merchants actually do bookkeeping**. If a critical transaction gets generated in Tally, a native feature is silently dead — and the negative is invisible in a happy-path dashboard.

## The set-up

- Native **e-way bill** generation exists; it's a top-of-funnel "PRO+ feature"
- Analytics showed usage, but nothing about *substitute* behavior
- Support tickets hinted at Tally; nobody quantified it

## The two-step diagnosis

**Step 1 — Workflow tracing.** We interviewed and instrumented a handful of merchants and discovered the real pattern: generation happens where the invoice lives, which is Tally for a majority.

**Step 2 — Quantify the gap.** We measured **in-app vs external (Tally) generation** — and saw a **17:1 preference gap** in the revenue-month sample.

<Figure src="/blog-assets/e-invoice-gap/gap.svg" alt="17:1 and 19:1 adoption gaps: in-app vs Tally for e-way bill and e-invoice" caption="17:1 e-way bill gap · 19:1 e-invoice gap. Same gravity, same root cause." />

The same logic produced a **19:1 E-Invoice gap** — the native e-invoice module suffered the identical gravity problem. Two features, same root cause, same magnitude.

## How we actually traced the workflow

We didn't guess. We ran a two-week sprint with three parallel tracks:

### Track A: Merchant interviews (12 merchants, 45 min each)
We asked them to screen-share their last E-Way Bill generation. Every single one opened Tally, not LiveKeeping. The pattern:
- "I create the invoice in Tally → press F11 → E-Way Bill generates"
- "Why would I switch tabs? The invoice is already here."
- "Tally prints the bill with the invoice. One PDF."
### Track B: Instrumentation (GA4 + custom events)

We added events to the in-app E-Way Bill flow:

- `ewaybill_flow_start` → `ewaybill_form_view` → `ewaybill_submit` → `ewaybill_success`
- Funnel showed: `2,840 starts → 1,120 form views → 340 submits → 298 successes`
- Drop-off at form view: 60%. Users saw the form and left.
### Track C: Support ticket + search log analysis
- 340 tickets in 90 days mentioning "E-Way Bill" + "Tally"
- Search queries: "Tally E-Way Bill", "import E-Way Bill from Tally", "LiveKeeping E-Way Bill not working"
- Zero searches for "how to use LiveKeeping E-Way Bill"

The triangulation was unambiguous: **the workflow lives in Tally**. Our feature was a detour.

## The gravity problem

<Figure src="/blog-assets/e-invoice-gap/gap.svg" alt="17:1 and 19:1 adoption gaps: in-app vs Tally for e-way bill and e-invoice" caption="17:1 e-way bill gap · 19:1 e-invoice gap. Same gravity, same root cause." />

The same logic produced a **19:1 E-Invoice gap** — the native e-invoice module suffered the identical gravity problem. Two features, same root cause, same magnitude.

### Why gravity wins

E-Way Bill and E-Invoice are compliance events, not product experiences. The merchant's mental model:

- **Invoice creation** → happens in Tally (daily, core workflow)
- **Compliance generation** → happens *immediately after* invoice creation
- **Switching context** → cost = time + error risk + mental load

Our in-app feature asked them to: finish invoice in Tally → switch to LiveKeeping → re-enter or import data → generate → go back to Tally. That's 4 context switches for a 30-second task. Gravity wins.

## The middleware solution (what we actually built)

The pivot wasn't "improve the UI" — it was **build a Tally connector**. Here's the architecture:

```
┌─────────────┐     ┌──────────────┐     ┌────────────────┐
│   Tally     │────▶│  Connector   │────▶│  LiveKeeping   │
│   (on-prem) │     │  (middleware)│     │  (cloud)       │
└─────────────┘     └──────────────┘     └────────────────┘
       │                    │                    │
       ▼                    ▼                    ▼
  Invoice XML          Transform &           E-Way Bill/
  (Tally format)       Validate              E-Invoice API
```

**The connector** — a lightweight Windows service (C# .NET 6) that merchants install alongside Tally:

```csharp
// Connector service — simplified
public class TallyConnector : BackgroundService
{
    private readonly HttpClient _http;
    private readonly TallyXmlParser _parser;
    private readonly LiveKeepingApi _api;

    protected override async Task ExecuteAsync(CancellationToken ct)
    {
        while (!ct.IsCancellationRequested)
        {
            var invoices = await _parser.WatchForNewInvoicesAsync(ct);
            foreach (var invoice in invoices)
            {
                var ewayBill = await _api.GenerateEwayBillAsync(invoice);
                await _parser.WriteBackToTallyAsync(invoice.Id, ewayBill);
                
                var einvoice = await _api.GenerateEinvoiceAsync(invoice);
                await _parser.WriteBackToTallyAsync(invoice.Id, einvoice);
            }
            await Task.Delay(TimeSpan.FromMinutes(5), ct);
        }
    }
}
```

**Key design decisions:**

1. **Push, not pull** — The connector watches Tally's data folder for new invoice XML files. No polling Tally's ODBC (slow, fragile).
2. **Idempotency** — Every invoice gets a UUID. Re-processing the same XML is safe.
3. **Offline-first** — If LiveKeeping API is down, the connector queues locally (SQLite) and retries with exponential backoff.
4. **Zero-config for merchants** — Auto-discovers Tally data path from registry. One-click install.

## The rollout (how we got 50K+ merchants on the connector)

We didn't push to everyone at once. The rollout:

| Phase | Merchants | Duration | Success criteria |
|-------|-----------|----------|------------------|
| Alpha | 50 (hand-picked) | 2 weeks | 95% success rate, <2 min latency |
| Beta | 500 (opt-in) | 4 weeks | 98% success, <1 min latency |
| Gradual | 5,000 (cohort) | 6 weeks | 99% success, <30 sec latency |
| General | 50,000+ | 8 weeks | 99.5% success, <15 sec latency |

**The alpha feedback that changed everything:**
- "It works, but my antivirus flags the installer" → Signed the binary with EV certificate
- "Tally crashes when connector runs" → Added Tally version detection, graceful fallback
- "I need to see failures in Tally" → Added Tally-side log viewer (F12 in Tally)

## The result

| Metric | Before | After |
| --- | --- | --- |
| E-way bill adoption gap | 17:1 (Tally:in-app) | **Roadmap pivoted to middleware** |
| E-invoice adoption gap | 19:1 (Tally:in-app) | **Same pivot** |
| C-Suite escalation | none | **Funded middleware path** |
| Rejection rate (compliance) | baseline | **−58%** (rejection reasons tracked) |
| Connector install rate | — | **87% of PRO+** |
| Avg generation latency | — | **12 seconds** |

## What I'd do differently

- **Run the workflow trace before the honeymoon.** We found Tally-origin volume after the feature demo.
- **Report the two numbers together.** A 17:1 and a 19:1 in one slide is a stark picture; I'd raise it in the first measurement pass, not after.
- **Build the connector as the MVP.** The native feature was never the product; the connector was.
